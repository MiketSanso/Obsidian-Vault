### **1. Значимые и ссылочные типы (Value Types vs Reference Types)**

- **Значимые типы (Value Types):** К ним относятся структуры (`struct`), перечисления (`enum`) и примитивы (например, `int`, `float`, `bool`). **Переменная значимого типа содержит само значение.** Они обычно размещаются **на стеке** (быстрый доступ, время жизни привязано к контексту метода), но могут быть помещены в кучу, если являются частью ссылочного типа (например, поле в классе) или упакованы (boxing).

- **Ссылочные типы (Reference Types):** К ним относятся классы (`class`), интерфейсы (`interface`), массивы, делегаты (`delegate`). **Переменная ссылочного типа содержит не сами данные, а ссылку (адрес в памяти) на объект в управляемой куче (heap).** Сам объект создается в куче.


### **Разница между структурами (struct) и классами (class)**

|Аспект|Структура (struct)|Класс (class)|
|---|---|---|
|**1. Тип**|Значимый (Value Type)|Ссылочный (Reference Type)|
|**2. Расположение в памяти**|**Стек** (если не является частью класса/не упакована). Быстрый аллокаций и очистка.|**Управляемая куча (Heap)**. Контролируется Garbage Collector (GC).|
|**3. Копирование**|**Копирование по значению.** При присваивании (`structB = structA`) или передаче в метод создается **полная копия** всех данных. Изменения в копии не затрагивают оригинал.|**Копирование по ссылке.** При присваивании (`classB = classA`) копируется только ссылка. Обе переменные начинают указывать на **один и тот же объект** в куче.|
|**4. Наследование**|**Не поддерживают наследование.** Не могут быть абстрактными и наследоваться от других struct/class. **Могут реализовывать интерфейсы.**|**Поддерживают полное наследование** (одиночное) и полиморфизм.|
|**5. Конструктор**|Не может содержать явного конструктора **без параметров**. Все поля должны быть явно инициализированы в любом конструкторе.|Может содержать конструктор без параметров (если не определен другой, он генерируется автоматически).|
|**6. Null**|Не может быть `null` (до появления nullable value types с `Nullable<T>` или синтаксиса `int?`).|По умолчанию имеет значение `null` (ссылка никуда не указывает).|


### **Boxing и Unboxing**

- **Boxing (Упаковка)** — это процесс **неявного** преобразования значимого типа в ссылочный тип (чаще всего в `object` или в интерфейс, который реализует структура).

  **Как происходит:** Значение со стека копируется в новый объект в управляемой куче. Переменная типа `object` начинает хранить ссылку на этот новый объект.

  **Проблемы (Минусы):**

1. **Производительность:** Аллокация памяти в куче и операция копирования данных — дорогостоящие операции.
            
2. **Давление на Garbage Collector (GC):** Созданный упакованный объект становится мусором, который must быть собран GC. В Unity, где важно избегать частых срабатываний GC для поддержания высокого FPS, бесконтрольный boxing — одна из частых причин просадок производительности.

 **Пример:** `int health = 100; object obj = health; // Boxing!`


- **Unboxing (Распаковка)** — это процесс **явного** извлечения упакованного значения из кучи обратно в значимый тип на стек.

  **Как происходит:** Проверяется, что целевой значимый тип соответствует упакованному типу. Если проверка прошла, значение копируется из кучи в стековую переменную.

  **Проблема:** Также требует затрат на проверку типа и копирование.
  **Пример:** `int newHealth = (int)obj; // Unboxing`


### **Реализация интерфейсов в структурах и боксинг**

 **Суть проблемы:** Когда структура (значимый тип) реализует интерфейс, и мы приводим экземпляр структуры к этому интерфейсу, происходит **боксинг (boxing)**.
    
 **Почему это происходит:** Интерфейс в .NET является ссылочным типом. Для того чтобы работать со значимым типом через ссылку, среда исполнения (CLR) должна упаковать его — то есть скопировать значение из стека в управляемую кучу и получить на него ссылку.
    

   **Пример и последствие (из комментария ментора):**
    
    csharp
    
    interface IDisposableFlag
    {
        void Dispose();
    }
    
    struct MyStruct : IDisposableFlag
    {
        public bool weDisposed;
        public void Dispose()
        {
            weDisposed = true;
        }
    }
    
    // Использование:
    MyStruct myStruct = new MyStruct();
    ((IDisposableFlag)myStruct).Dispose(); // <- ЗДЕСЬ ПРОИСХОДИТ BOXING!
    
    Console.WriteLine(myStruct.weDisposed); // Выведет False!
    
**Объяснение:** Строка `((IDisposableFlag)myStruct).Dispose()` создает _копию_ `myStruct` в куче (упаковывает ее). Метод `Dispose()` вызывается у этой упакованной копии, а исходная структура `myStruct` на стеке остается неизменной.

   **Как избежать боксинга:**  
Единственный эффективный способ — использовать **обобщенный метод (generic method)** с ограничением типа (`where T : IInterface`). Это позволяет компилятору вызвать метод напрямую для структуры без приведения к интерфейсу.

	// Правильный способ без боксинга
	public static void CallDispose<T>(ref T disposable) where T : IDisposableFlag
	{
		disposable.Dispose();
	}
	
	// Использование:
	CallDispose(ref myStruct); // Боксинг не происходит!
	Console.WriteLine(myStruct.weDisposed); // Выведет True!
	
	В этом случае компилятор генерирует специализированную версию метода для типа `MyStruct`, и вызов метода `Dispose()` происходит напрямую, без упаковки

### **2. Коллекции: сложность операций**

| Коллекция              | Добавление (Add)   | Вставка (Insert) | Удаление (Remove) | Поиск по индексу (Index) | Поиск по значению (Contains) | Доступ (Peek/Dequeue) |
| ---------------------- | ------------------ | ---------------- | ----------------- | ------------------------ | ---------------------------- | --------------------- |
| **`T[]` (Array)**      | -                  | -                | -                 | **O(1)**                 | O(n)                         | -                     |
| **`List<T>`**          | **O(1)** или O(n)* | O(n)             | O(n)              | **O(1)**                 | O(n)                         | -                     |
| **`Dictionary<K, V>`** | **O(1)**           | -                | **O(1)**          | -                        | **O(1)** (по ключу)          | -                     |
| **`HashSet<T>`**       | **O(1)**           | -                | **O(1)**          | -                        | **O(1)**                     | -                     |
| **`Queue<T>`**         | **O(1)**           | -                | -                 | -                        | -                            | **O(1)** (Dequeue)    |
| **`Stack<T>`**         | **O(1)** (Push)    | -                | -                 | -                        | -                            | **O(1)** (Pop)        |
| **`LinkedList<T>`**    | **O(1)**           | **O(1)****       | **O(1)****        | O(n)                     | O(n)                         | -                     |

**Пояснения к таблице:**

- **`List<T>.Add`:** В среднем **O(1)**. Если внутренний массив заполнен, требуется создание нового массива (вдвое большего) и копирование всех элементов, что занимает **O(n)** времени.

- **`List<T>.Insert` / `Remove`:** **O(n)**, так как требует сдвига всех элементов, следующих за целевым.

- **`LinkedList<T>.Insert` / `Remove`:** **O(1)**, но только если у вас уже есть ссылка на узел, в котором нужно произвести операцию. Поиск этого узла по индексу или значению все равно займет O(n).



> _"Если у тебя заранее известно количество элементов, то нет смысла использовать `List<T>`. Это может сигнализировать другому разработчику, что коллекцию можно расширять, что может быть неверно. Например, для матча на 10 игроков логичнее использовать массив `Player[10]`."_

**Вывод:** Выбор коллекции — это не только про производительность, но и про **намерение** в коде. Массив фиксированного размера четко говорит о том, что расширение не предполагается.


### **Как работает Dictionary "под капотом"**

**Внутреннее устройство:** Внутри `Dictionary<K, V>` хранит два массива:

1. **Массив бакетов (buckets):** Содержит индексы (указатели) на элементы в другом массиве.

2. **Массив записей (entries):** Содержит непосредственно данные: хэш-код ключа, ключ, значение и ссылку на следующую запись в цепочке (для разрешения коллизий).

**Алгоритм работы:**

 1. **Вычисление индекса:** Когда вы вызываете `myDict[key]`,

- Вычисляется хэш-код ключа (`key.GetHashCode()`).
   
- Этот хэш-код преобразуется в индекс бакета с помощью операции `hash % buckets.Length`.

2. **Поиск в цепочке:**

    - Берется индекс из найденного бакета. Это индекс первой записи в цепочке для этого бакета.
            
        - Происходит последовательный обход цепочки записей. Для каждой записи проверяется:
        
            - Совпадает ли хэш-код (для быстрого отсечения).
            
            - **Совпадает ли ключ по значению** (через `key.Equals(entry.Key)`). Этокритически важный шаг.
            
        - Если запись найдена — возвращается ее значение.
            
        - Если конец цепочки достигнут, а совпадения нет — элемент не найден.
            
- **Проблема, если ключ — изменяемый класс (Важный комментарий ментора):**
    
    > _"Если ключ — это класс, и я создаю два экземпляра с одинаковыми данными, я не смогу найти значение по второму ключу, потому что хэш-код по умолчанию — это указатель на объект в памяти."_
    
    **Решение:** Для использования кастомных классов в качестве ключа **необходимо**:
    
    1. **Переопределить метод `GetHashCode()`.** Он должен возвращать одинаковый числовой хэш для объектов, которые считаются равными. Хэш должен быть стабилен на протяжении жизни объекта.
        
    2. **Переопределить метод `Equals()`.** Он должен содержать логику сравнения объектов по значению полей, а не по ссылке.
        
    
    **Следствие:** Если изменить поле объекта, которое используется в расчете хэша, после того как объект уже добавлен в словарь в качестве ключа, то `GetHashCode()` начнет возвращать другое значение. Поиск по такому ключу приведет к неправильному бакету, и элемент **не будет найден**. Поэтому ключи должны быть **неизменяемыми (immutable)**.
    


### **Как массив лежит в памяти**

- **Массив значимых типов (например, `int[]`, `Vector3[]`):**
    
    > _"Если у нас массив интов, то он просто кладется в памяти рядом. Все наши 10 интов в массиве лежат последовательно, одним непрерывным блоком."_
    
    - Это обеспечивает **пространственную локальность** и максимальную скорость итераций (кэш процессора используется эффективно).
        
- **Массив ссылочных типов (например, `GameObject[]`, `string[]`):**
    
    > _"Если у нас массив классов, то сами классы не лежат внутри массива. У нас в массиве лежат указатели на них."_
    
    - В памяти сам массив — это непрерывный блок не самих объектов, а **ссылок** (указателей) на них.
        
    - Объекты, на которые ссылаются эти указатели, расположены в управляемой куче в произвольных местах.
        
    - **Причина:** Это позволяет реализовать полиморфизм. В массиве `Component[]` можно хранить объекты разных размеров (например, `Transform`, `Rigidbody`, `MyCustomScript`), так как массив содержит лишь ссылки одинакового размера.
        
- **Доступ к элементу:** В обоих случаях доступ по индексу `arr[i]` выполняется за **O(1)**, так как адрес вычисляется по формуле: `адрес_начала_массива + (размер_элемента * i)`. Для ссылочных типов "размер элемента" — это размер указателя (например, 4 или 8 байт).

 3. Задача на список векторов (List <Vector3>)

- **Суть проблемы:** Взаимодействие с элементами коллекций значимых типов (как `Vector3` в `List<T>`) имеет важную особенность, связанную с тем, что структуры копируются по значению.
    
- **Код, о котором говорит ментор:**
    
    csharp
    
    Vector3[] array = new Vector3[1];
    array[0] = Vector3.zero; // Кладем вектор (0,0,0) в массив
    
    List<Vector3> list = new List<Vector3>();
    list.Add(Vector3.zero); // Кладем такой же вектор в список
    
    array[0].x = 100; // Попытка изменить X у элемента массива
    list[0].x = 100;  // Попытка изменить X у элемента списка -> ОШИБКА КОМПИЛЯЦИИ!
    
- **Почему возникает ошибка:**
    
    1. **Для массива (`array[0].x = 100`):**
        
        - Оператор доступа к элементу массива `[]` возвращает **ссылку на саму структуру** в памяти массива. Это позволяет напрямую менять ее поле.
            
    2. **Для списка (`list[0].x = 100`):**
        
        - Индексатор списка `list[0]` возвращает не ссылку, а **копию** структуры, хранящейся внутри списка.
            
        - Строка `list[0].x = 100` пытается изменить поле `.x` у этой временной копии. После выполнения строки копия сразу же уничтожается, а исходный вектор внутри списка остается неизменным.
            
        - Компилятор C# знает, что эта операция бессмысленна (поскольку меняется копия, а не оригинал), и **запрещает ее на уровне компиляции**, чтобы разработчик не совершил логическую ошибку.
            
- **Как правильно изменить элемент в списке:**  
    Поскольку нельзя изменить поле одного элемента структуры напрямую, нужно заменить весь элемент целиком:
    
    csharp
    
    Vector3 tempVector = list[0]; // Получаем копию элемента
    tempVector.x = 100;           // Меняем нужное поле у копии
    list[0] = tempVector;         // Заменяем весь элемент в списке на измененную копию
    
- **Важный комментарий ментора о Capacity и Count:**
    
    > _"Я формально не должен иметь доступ к элементу с индексом 8, если в списке всего 1 элемент. Каплятор (компилятор) предпочитает, чтобы этой хуйнёй не занимались. Даже если бы это было возможно, я бы просто получил копию 'дефолтного' вектора, поменял бы ее, и она бы просто пропала, не изменив сам список."_
    
    - `List<T>` имеет `Capacity` (вместимость, размер внутреннего массива) и `Count` (фактическое количество элементов). Обращение к индексу >= `Count` (даже если он < `Capacity`) выбросит `ArgumentOutOfRangeException`, чтобы предотвратить работу с "мусорными" данными, которые лежат в зарезервированной, но неиспользуемой памяти.

### **6. String, StringBuilder, Интернирование строк**

- **Неизменяемость (Immutability):** Строки (`string`) в C# являются **неизменяемыми**. Это означает, что после создания строки ее содержимое нельзя изменить. Методы типа `.Replace()`, `.ToUpper()` и оператор `+` (**конкатенация**) на самом деле **создают новый строковый объект** в памяти, а старый остается неизменным.
    
- **Проблема конкатенации в циклах:** Многократное использование `+` или `String.Concat` в цикле приводит к созданию огромного количества промежуточных строк-мусора, что сильно нагружает память и сборщик мусора (GC), особенно в Unity.
    
- **Интернирование строк (String Interning):**
    
    > _"Это нужно, чтобы мы не занимали память каким-то копипастом строк. Если я тысячу раз пишу имя игрока 'Миша', у меня не должно быть в памяти тысячу раз строки 'Миша'."_
    
    - **Интернирование** — это механизм CLR, который хранит **только одну уникальную копию** каждого литерала строки в специальной области памяти ("пул интернированных строк").
        
    - При создании новой строки CLR проверяет пул. Если такая строка уже есть, возвращается **ссылка на существующий объект**, а новый не создается.
        
    - Этот процесс в основном **автоматический** для строковых литералов, написанных прямо в коде. Явное интернирование можно сделать через `String.Intern()`.
        
- **StringBuilder:**
    
    > *"Поэтому придумали StringBuilder. Его фишка в том, что он хранит массив чаров (символов)."
    
    - `StringBuilder` — это класс для **эффективного построения строки** без создания множества промежуточных объектов.
        
    - **Как работает:** Он внутри хранит символы в массиве. При добавлении новых данных он проверяет, хватает ли места. Если нет — **увеличивает емкость** (обычно в 2 раза, как `List<T>`).
        
    - **Эволюция (по комментарию ментора):** В современных версиях .NET для очень больших строк `StringBuilder` может использовать **связанный список** из нескольких массивов, чтобы избежать создания одного огромного массива, который может попасть в **Large Object Heap (LOH)**. Объекты в LOH хуже поддаются сборке мусора и могут вызывать паузы в производительности.
        
- **Когда что использовать:**
    
    - **`string`:** Для большинства операций, для строк, которые не меняются.
        
    - **`+` или `string.Format`:** Для простой конкатенации 2-5 строк.
        
    - **`StringBuilder`:** Когда нужно собрать строку в цикле или через множество операций конкатенации.

### **7. Интерфейсы vs Абстрактные классы**

|Аспект|Интерфейс (`interface`)|Абстрактный класс (`abstract class`)|
|---|---|---|
|**Наследование**|Класс или структура могут реализовать **множество интерфейсов**.|Класс может наследоваться только **от одного** абстрактного класса.|
|**Реализация по умолчанию**|Начиная с C# 8.0, можно иметь **реализацию по умолчанию** для методов и свойств.|Может содержать полную реализацию одних методов и абстрактные члены других.|
|**Поля (fields)**|**Не могут** содержать поля экземпляра (только свойства и события).|**Могут** содержать поля, свойства, события, константы.|
|**Конструкторы**|Не могут иметь конструкторов.|Могут иметь конструкторы (вызываются конструкторами дочерних классов).|

### **8. Делегаты и Замыкания**

- **Делегаты (Delegates):** Это типобезопасные указатели на методы. Позволяют передавать методы как аргументы, хранить их в переменных и т.д. (`Action`, `Func`, `Predicate`).
    
- **Замыкания (Closures):**
    
    > _"Замыкание — это когда делегат замыкается на каком-то внешнем поле."_
    
    - **Замыкание** — это способность анонимного метода (или лямбда-выражения) **"запоминать"** и иметь доступ к переменным из окружающего его контекста, даже после того, как выполнение кода вышло из этого контекста.
        
    - **Как работает:** Компилятор C# автоматически создает скрытый вспомогательный класс, в который "поднимает" (captures) захватываемую переменную. И делегат, и внешний код работают уже с полем этого класса.
        
- **Задача на замыкания (Классическая проблема с циклом и делегатом):**
    
    csharp
    
    List<Action> actions = new List<Action>();
    for (int i = 0; i < 10; i++)
    {
        actions.Add(() => Console.WriteLine(i));
    }
    actions[0](); // Выведет не 0, а 10!
    
    **Объяснение (из комментария ментора):**
    
    > _"Мы передаем переменную цикла `i`, и неочевидно, что в делегате потом она после выхода из цикла будет везде равна 10."_
    
    - Делегаты захватывают **не значение** переменной `i` на момент создания делегата, а **саму переменную** (ссылку на нее).
        
    - Все делегаты в списке ссылаются на **одну и ту же** переменную `i`.
        
    - К моменту вызова `actions[0]()` цикл уже давно завершился, и значение переменной `i` равно **10**.
        
    - Поэтому вызов любого делегата из списка выведет значение `i` на момент вызова, то есть 10.
        
- **Решение (как зафиксировать значение):**  
    Нужно создать **локальную копию** переменной на каждой итерации цикла. Ее значение будет захватываться правильно.
    
    csharp
    
    for (int i = 0; i < 10; i++)
    {
        int temp = i; // Копия для данной итерации
        actions.Add(() => Console.WriteLine(temp));
    }
    actions[0](); // Выведет 0
    actions[1](); // Выведет 1
